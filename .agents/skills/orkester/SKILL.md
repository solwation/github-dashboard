---
name: orkester
description: Coordinate parallel work on this repository when the user invokes /orkester, $orkester, or explicitly asks for a conductor and subagents.
---

Read the repository's root AI.md. Act as the conductor: own the task breakdown, issue assignments, integration, verification and final report.

The session runs unattended. Never ask questions in chat, pause for confirmation or end a turn waiting for an answer. Decide routine choices yourself and document the reasoning on the issue. When a decision genuinely belongs to the user, post one issue comment with concrete options and your recommendation, add the `user question` label, release the claim and continue with the next actionable issue. Skip `user question` issues until the user answers; the session that resumes one removes the label. `user question` never blocks publication; use `blocked` only for real technical blockers, since it stops the Action gate.

Start the requested workflow immediately. Inspect open issues and existing claims; identify independent work and actual dependencies. Continue within the user's authorized scope. If no scope is provided, select actionable unclaimed issues by priority, oldest first; do not expand an explicitly bounded task into the entire backlog.

**Size concurrency from the measured free capacity of the machine you run on, with no fixed cap** (a stronger machine runs more workers): `free_cores = nproc − max(0, load1 − own load)`, `free_mem = MemAvailable − 2 GiB`, capacity = `min(floor(free_cores / 1.5), floor(free_mem / 1.5 GiB))`, counting browser-suite workers as 2 cores and 2 GiB, and always at least one active issue. Target each issue landing on main within 30 minutes; split larger issues into GitHub sub-issues that each land within 30 minutes before assigning them. Count this session's own claims, including its workers and the conductor's own implementation, review, integration and verification. Other sessions' claims have their own limits; respect them and avoid overlapping file ownership. Tool slots and independent files may reduce concurrency further. Reserve resources for the conductor and browser testing; do not fill all tool slots automatically. If subagent tools are unavailable, explain that and run the same issue flow sequentially.

Before every assignment, resume or integration:

1. Fetch the complete open issue queue with pagination and inspect all active claims.
2. Record each active issue number, owner and phase (implementation, review, integration or verification). Count this session's claims, including the conductor's work.
3. Remove this session's active/owner labels from delivered work immediately when it enters a waiting queue. Never change another session's claim. Waiting for deployment does not keep a slot active; reclaim one when verification actually begins.
4. Re-measure free capacity and check that the proposed work is independent and this session's resulting total fits it. If capacity is full, finish or pause something first. Register new user requests in the backlog without immediately starting them.
5. Claim the issue, re-read the queue to detect races, then start. Preserve every paused worktree and commit. On worker delivery, release the claim before assigning the worker another issue; review/integration must reclaim capacity through this same check.

Give each worker one issue, acceptance criteria, explicit file ownership, dependencies and a separate Git worktree/branch. Use a common committed baseline. Workers may share read-only dependencies only; they must not change shared node_modules or lockfiles concurrently. The conductor owns package changes, overlapping integrations and final pushes to main. Where files overlap, workers return isolated commits and the conductor resolves them deliberately; never overwrite another worker's changes.

Mark actively worked issues in-progress. Each worker handles one issue at a time and returns its commit, tests and integration notes. Workers do not push main or close issues before the conductor validates their integration. Remove active and owner labels immediately on pause or delivery into the integration queue, and on completion. An unintegrated result is not an active worker assignment.

Review and integrate commits in dependency order and run appropriate combined local checks. Integration pushes are allowed while the backlog has work; they do not authorize publication. GitHub Actions alone decides whether to deploy through its fresh queue and metadata gates. Never manually deploy or bypass those gates. Verify GitHub Pages after an Action actually publishes. Keep progress updates concise. Report completed issues and genuine outstanding work. Preserve unfinished branches/worktrees until their work is safely integrated; never discard unknown work while cleaning up.

Do not end the session immediately when the queue becomes empty. Whenever the actionable queue is empty and the latest batch is published and verified on Pages, first conduct a thorough review of the completed work (commits, tests, acceptance criteria and live behavior) that has not yet been reviewed in its final state. If the review finds any defect, regression or unmet acceptance criterion, either reopen the affected issue with a comment explaining what remains (clearing any stale work or `needs-deploy` labels) or create a new issue with an assessed priority, rationale and concrete acceptance criteria to cover the gap, then immediately continue the `/orkester` workflow. Once the last issue is solved, the combined batch is published, Pages verification succeeds and the post-work review finds no issues, record that time and monitor for another 60 minutes. Poll the complete paginated GitHub issue queue about every 60 seconds, using interruptible waits no longer than 60 seconds. New user input interrupts the wait and steers the session normally. Idle monitoring holds no `in-progress` or owner claims and requires no scheduled jobs or external messages.

When new or review-triggered issues arrive, resume within the authorized scope using the normal priority, fresh-queue, claim and capacity checks. Implement, integrate and test new work, push integrations as needed, and let the Action gate decide when the combined publication is ready. After the last issue is solved, published, verified and passes the empty-queue review, reset the monitoring deadline to 60 minutes later. End only after 60 minutes without new work or the user's explicit instruction to stop.


## Practices adapted from Lunden's orkester workflow

- Fetch the complete current queue with pagination before each assignment. Recheck labels and claims immediately before starting. Sort by high/medium/low priority, then creation time; future reservations do not override a fresh queue or explicit user scope. Coordination issues labelled exactly `orkester` are not work.
- Give a session a stable `orkester: <id>` owner label when several orchestrators share this repository. Apply it together with `in-progress` only during real work, remove both on pause/closure, and never remove another session’s claim. Owner labels are metadata, not priority. If sessions cannot communicate directly, maintain one status comment in a coordination issue labelled `orkester`; record issue, agent, file/module ownership, worktree and latest checkpoint. Re-read claims after reserving to detect races; the earlier valid reservation wins.
- Group related changes to the same files under one owner and execute them sequentially. Keep assignments short; workers return after their current issue and wait for a fresh assignment instead of automatically advancing through a reserved chain. Avoid formatting or dependency changes in files another worker owns.
- In WSL, prefer worktrees on the Linux/ext4 filesystem rather than `/mnt/c`. Give browser tasks distinct ports and screenshot directories. Do not run many headless browser suites simultaneously; the conductor schedules the combined suite.
- Monitor checkpoints rather than just process liveness. Ask for a concrete progress report after roughly 30 minutes without a commit or useful result; inspect stalled browser/build processes and reduce/split work if progress remains absent. Preserve existing worktrees and commits when a worker stops; resume from them rather than rebuilding the same changes.
- Integrate and test small increments locally; the conductor may push integrations to main while work remains, but only GitHub Actions authorizes publication. Its full paginated queue gate runs before building and immediately before deployment on pushes, issue opening/reopening/closing/label changes and gated workflow dispatch. Blocked, active or owner-claimed work, and delta issues lacking `needs-deploy`, prevent publication; PRs, exact `orkester` coordination issues and unclaimed backlog outside the delta are excluded. After 3 hours without a publication, claims outside the prepared delta stop blocking (an hourly scheduled run triggers this fallback), so unfinished work must never reach main, claimed or not, and every integration keeps the delta and release notes current. Open `needs-deploy` issues pass only if unclaimed and included in the prepared delta, so publication does not depend on closing them first. Never auto-mark readiness or manually bypass the Action. Prepare a bilingual summary of at most 180 characters per language against the actual public build commit, with issue references in daily notes. The gates bind it to current main, the fresh public baseline and the exact deployment artifact, fail closed on missing/stale metadata and skip already published SHAs. After the Action publishes, verify Pages and close/clear delivered ready issues. Preserve all capacity, isolation and 60-minute idle-monitoring rules.

These practices are adapted from `lunden-3d-apartment/.claude/commands/orkester.md`; game-specific rules, issue numbers and its fixed VM CPU assumptions do not apply here.
