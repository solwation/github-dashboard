# Issueflow feature reference

Detailed behavior, settings and contributor notes. For the short overview, see the [README](../README.md).

One view of what your agents plan, work on and complete across your repositories. Follow AI agents that use GitHub issues as their work queue, or track issues you handle yourself. Backlog sorts by priority, active work shows elapsed time, and Closed keeps the last 30 days in view.

- **Public repositories without a key:** choose **Follow public repositories** on the welcome screen, add `owner/repo` names or GitHub repository URLs, then choose **Show overview**. Public mode supports cards, lists, filters, local rules, estimates and available REST statistics. Its catalog, preferences and whole repository snapshots are encrypted in a separate local profile; saved account credentials and private content remain separate. Reload reuses snapshots for up to 24 hours without API requests, and changing selection loads only missing or expired repositories. The content cache keeps at most 100 complete repositories within 4 MiB; oversized or incomplete repositories are fetched normally. Failed refreshes retain the last successful data and sync time, without extending its age. Closed issues still leave the view after 30 days. Refresh manually from the repository status or with Ctrl/Cmd+R/F5; public mode does not poll or register background collection. GitHub allows 60 anonymous REST requests per hour per IP, so work-start history uses at most two shared event pages per repository, and missing history stays unknown. GraphQL-only details stay hidden. Leave the public workspace to return to sign-in.
- **Find issues:** combine the global text filter with independent filters per repository; open the search button in a repository header to search titles, issue numbers and labels, and clear each repository filter separately. The button marks an active query even when the field is closed; Escape closes the field and returns focus to the button. On phones a collapsed repository hides its search field and shows its settings button beside the summary, so the card stays short; the query is kept and applies again when expanded.
- **Column sort order:** the hint beside each column title is a button that opens a small menu. Backlog offers highest priority first (default), lowest priority first, oldest first and newest first; In progress longest running first (default), most recently started first and priority; Closed newest closed first (default), oldest closed first and priority. The active option is checked (`menuitemradio`, `aria-checked`) and shown in the hint. Open it with a click or tap, or with Enter, Space or the arrow keys; arrows, Home and End move, Enter or Space chooses and Escape closes and returns focus to the hint. The choice is per column, applies to Cards, List, split and combined boards, and is kept as a non-private preference in this browser; choosing the default option resets it.
- **Grouping: Joined, Split or Swimlanes:** The **Group by repository** control in the board toolbar (Swedish **Gruppering per repository**: Samlad, Dela upp, Simbanor) chooses how selected projects are arranged in both Cards and List, and switching Cards/List keeps the choice. **Split** (the default) shows a separate board per repository; **Joined** shows one combined board covering every selected project; **Swimlanes** shows one combined board with a lane per project. In Cards the lanes are horizontal bands stacked below one shared status header row (status, total count, estimate and sorting), which stays below the top bar while you scroll; each band has the project's colour stripe, heading, collapse toggle and per-status counts, and empty status cells keep a compact empty note. In List, repository columns form one joined table with shared Backlog, In progress and Closed status bands. Cells in each status row align across all projects, including when an issue expands, and project columns have no collapse controls. Narrow screens keep the same table and scroll sideways inside the view; Cards bands still stack on phones. Swimlanes, like Joined, use the main search alone; per-repository searches, sync controls and settings stay in the split view. Sidebar activation reveals the project column in List; in Cards, activating a project again collapses or expands its band. The choice is saved per account in the encrypted settings and follows QR sync; earlier settings and QR codes with the former Split by repository checkbox keep their effect (checked becomes Split, unchecked Joined), and the old setting is still written for older app versions. The buttons are keyboard operable and have 44px touch targets. In List swimlanes, a cell count appears only while its display limit hides additional issues; empty cells and cells showing all their issues omit it.
- **Split and Joined details:** Split lanes have compact headers with repository details, issue count and a sync time whose tooltip explains the last update; click the time to refresh. The combined sync control is in the filter toolbar, without an extra header row. On the combined board each card shows a repository badge in a contrasting palette color matching the sidebar dot. The combined board is filtered by the main search alone; per-repository searches apply only in the split view and keep their values. Color assignments stay stable when sorting or changing the selection, are saved per account and follow QR sync alongside the view choice. Combined columns use the global card limit. Select a sidebar repository to keep a matching colour frame around its cards and list rows, including after refresh or a view switch; select it again to clear. Other projects stay visible.
- **Cards or list:** One Cards/List switch at the far right of the board toolbar (after the grouping control on narrow screens) shows a compact row per issue with number, title, status, priority, main labels and time. It applies to every repository in the split view and to the combined board: Lists show a compact colored repository chip beside status and priority, while Cards keep the repository badge beside the issue number and show the title before a single line of labels, with a +N tooltip for remaining labels. Cards combine age or work time with comments and the description toggle in one compact metadata row. In combined cards and lists, repository labels omit the owner only when all selected repositories share that owner (case-insensitively), even if issue filters hide some repositories; full names remain in tooltips and screen-reader text. Filters, column limits, Show more, timeout and movement markers work in both modes. Desktop and tablet rows are two lines tall in Joined, Split and Swimlanes alike (#426, #435): the issue number is a square badge at the far left spanning both lines, with the type icon above the number, followed by a time stack (age, work time or closing date on line 1; estimate, remaining or actual time on line 2). The title gets the rest of line 1. Line 2 continues with the story points in a fixed slot, then priority (open work), repository chip (Joined), status and timeout in fixed slots, then labels, with Moved/New and new-comment markers at its end, so appearing or reading them does not change row height or chip positions; empty slots collapse instead of leaving gaps. Lists narrower than 600px (many swimlanes) keep the square over lines 1–2 and move the time stack to its own third line, left-aligned with the title. Repository chips hug their text within their reserved slot, and long labels leave the +N control visible. Desktop labels share one clipped line, with full text in their tooltips and expanded card, so long labels cannot push the timeout onto another line. Every list row, at every width including narrow swimlane columns and phones, shows the same comments button and total as Cards (#429) in a fixed slot at the end of line 2 (3.5rem on desktop and tablet; 2.75rem after the time fields on phones), with unread animation and an accessible name such as "3 kommentarer, 2 nya" instead of an extra +N badge. Totals from 10,000 are abbreviated in the row (99 tn, 99K) while the accessible name keeps the exact count. On touch screens a 44px hit area around it leaves the row height unchanged. Clicking, tapping, Enter or Space opens the existing comments dialog without expanding the row or opening the phone card popup, and closing it returns focus to the button. Desktop and tablet rows keep the separate +N ✓ mark-as-read marker; phones show unread comments on the comment button alone. Reduced motion keeps a static unread indicator. Phone rows use two compact lines. Landscape phones (wider than 480px) show the square number badge over both lines, with the title beside it above points, priority, repository/activity markers, separate time fields and the comment button. Portrait phones (480px and narrower) keep a one-line number badge before the title with points directly under it, because a square would leave line 2 no room for the repository chip beside long closed and actual times. Main labels and details remain in the full card popup. Short touch viewports keep the compact phone layout even above the portrait width breakpoint. On desktop and tablet, clicking a row (or Enter/Space on its title) expands all card details in place with the description already open; on phones, tapping a row opens the full card in a popup dialog. Expanded descriptions keep readable line lengths; wide rows can place standalone images on the right. The issue number in Cards and List is a badge filled with the repository's own color (the same as the sidebar dot and card stripe) with white or black text chosen for at least 4.5:1 contrast in light and dark themes; in Cards the type or status icon stays before it, and in List it sits inside the badge. The List square shows the number without # or ↗ so up to five digits (six with tighter spacing) fit at the 10px text floor; the link name, tooltip and copied text keep “#”, and portrait phones show “#” in their one-line badge. On cards, the title and upper surface toggle the description; only the issue number with ↗ opens that issue on GitHub. In List, the issue-number badge is a separate link that opens the issue on GitHub in a new tab; the whole square (44px on touch screens) is its target, and keyboard focus outlines the badge. Expanded rows are not saved. Large list mounts batch label sizing through the browser’s resize observer instead of forcing a layout for each row. The choice switches instantly without refetching, is saved in the encrypted account settings and follows QR sync. Earlier per-repository choices migrate automatically: with Split by repository off the combined board's choice wins, otherwise List applies when more than half of the selected repositories used it; older QR codes are read the same way. Story-point tooltips show estimated total time when sufficient filtered repository history exists. With that history and a known start, in-progress cards show remaining time and a compact elapsed-time bar at the bottom right; list rows show remaining time under the elapsed time in the left time stack (on phones in the rightmost column). Backlog uses the same column for an italic total estimate with ≈ when sufficient history exists. Overdue estimates are clearly marked. Closed rows and cards show observed work-start-to-close duration when known, with an up/down arrow against the point-based estimate calibrated from other recent closures; creation age never substitutes for work time. Closed list rows use that same slot for actual work duration and its comparison arrow, under the closing date; full descriptions remain in tooltips and the card.
- **Unread activity:** The Overview sidebar badge counts unseen recent events across selected repositories, including new comments and movement, using the existing two-minute activity lifetime and encrypted read acknowledgements. Search, row limits and collapse do not change it; hidden coordination issues and pull requests are excluded.
- **Your layout:** reorder projects, collapse repositories and set how many cards each column shows. On mobile, open Settings → Reorder repositories to drag handles or use up/down buttons; the order saves immediately and stays consistent with the desktop sidebar. A column expanded with Show more beyond its configured count shows a Collapse button (ChevronUp) that returns it to the configured count and then hides (#380, #437). In the Joined and Split boards it sits in the column header; in Swimlanes the cell header is hidden or shared, so it sits beside Show more at the foot of that repository's cell and resets only that cell (its accessible name includes status and repository). It works in Cards and List, by keyboard, with a 44px touch target. Expanding a collapsed repository resets Show more in all its columns to the configured global or repository limit, in both Cards and List mode. Selecting a collapsed repository in the sidebar expands it automatically and briefly outlines its container; reduced motion uses a static outline. Confirmed repository selections appear immediately; new projects show loading while existing data stays visible.
- **Hide projects from the board:** hover a project in the left menu (or reach it with Tab) and choose the eye button **Hide** to leave it out of the split and combined boards in Cards and List, without empty sections. It stays in the menu, greyed with a hollow dot, and works for your public and private projects and other people's public projects. Choose **Show**, or click the project itself, to bring it back. **Hide inactive repositories** (off by default; inactive projects are always listed below it) keeps inactive projects greyed in the menu and off the board; clicking one shows and selects or expands it for the session, and turning the setting off or on again resets those exceptions. Manual choices always win and survive turning automatic hiding off. Opening one of a hidden project's issues from a notification or parent link shows the project again. Phones show the same Show/Hide buttons in the left-menu drawer; touch screens and the 70px rail use Settings → Reorder repositories for the same buttons and setting, and tapping a greyed project shows it. Manual choices are saved in the encrypted account settings, never in localStorage; Statistics and notifications still include hidden projects; the overview summary's issue totals leave them out, while its Repositories card still counts every selected project. If every project is hidden, the board says so and explains how to show them.
- **Project links:** the sidebar action menu names the project once in its heading and uses short GitHub, website and Show/Hide actions. Sidebar project hover shows the full repository name; screen readers also receive counts, unread activity, hidden/loading state and the last change. Project actions open GitHub separately from the website: a valid HTTP(S) Website from repository settings takes precedence over the standard GitHub Pages fallback, in every project group.
- **Inactive after (minutes since last closed issue):** Settings → Board. A project with no open Backlog or In progress issues stays active, in the sidebar's active group, in **Hide inactive repositories** (its lane stays on the board), in the overview's active count and in Settings → Reorder repositories, until this many minutes after its most recently closed issue (`closed_at`, including a closing still pending verification). Default 30; whole minutes from 0 to 1440; 0 means inactive at once. The move happens by itself on the existing clock when the time runs out, without extra GitHub requests, and survives reload and cache restore because it is derived from the loaded issues. A project with no known close time, other people's public projects and unavailable projects follow the unchanged rules. The value is saved in the encrypted account settings, restored on sign-in and travels with the preference transfer (QR/link).
- **Left menu on phones:** the menu button at the left of the top bar (44px touch target, `aria-expanded`), or a swipe from the left edge, opens the left menu as a drawer with the same functions as the desktop sidebar in one compact column: Overview with its unread count, Statistics, repositories with counts, GitHub links and Show/Hide, Hide inactive repositories, add (+), the running version and the license link. Touch targets are at least 44px and long names end with an ellipsis. Swiping left, Escape, the backdrop, the close button or choosing a destination closes it (Escape returns focus to the top-bar button); nothing floats over the page content at the left edge; while closed it is skipped by keyboard navigation and screen readers.
- **Other people's public projects:** from the sidebar **+** menu (Select repositories) or Settings → Reorder repositories, add any public repository as `owner/repo` or a GitHub URL, even when you are not a member. Nonexistent, private or inaccessible repositories show a clear error and are not added; duplicates of your own or already added repositories are refused. They form their own group, **Other public projects**, below your active and inactive repositories in the sidebar and the phone drawer (the 70px rail shows it in Settings) and below your own projects in Settings. The group has its own order, shared by sidebar, Settings and board and independent of your own order; reordering never moves a repository between groups. Remove one with its Remove button in Settings or the selection dialog. The group is hidden entirely when empty. The list and its order are saved in the encrypted account settings (IndexedDB), never in localStorage or sessionStorage, and restore after sign-in; they are not shown in anonymous public mode, which has its own catalog.
- **Issue hierarchy:** parent cards show a compact closed/total badge; sub-issues link to their parent, including across repositories. Expanded card and list details group the closed/total count, progress bar and each sub-issue with Backlog, In progress or Closed status below the description, including repository-specific label rules. Available progress remains visible when individual sub-issues are inaccessible. The list loads on demand through paginated REST, works for public repositories without a key and shares a bounded ten-minute cache. Relations stay hidden when unavailable. Counts come from GitHub and are independent of dashboard filters.
- **The context you need:** read issue descriptions, comments shown newest first with live relative timestamps for the first seven days (exact time on hover), and closing commit details, including embedded images linked to GitHub repository files. Descriptions and comments show compact clickable thumbnails for Markdown images and direct HTTP(S) image links (PNG, JPEG, GIF, WebP, AVIF, SVG, BMP and ICO, including query strings and GitHub blob links, plus GitHub attachment URLs without extensions). GitHub release-asset images (`github.com/<owner>/<repo>/releases/download/<tag>/<file>`) load directly in the browser from that address, without API requests or token, so assets in public repositories are shown in the comment, the image carousel and the viewer; an asset the browser cannot load (for example in a private repository, or a deleted asset) shows a placeholder with its name and a **Visa på GitHub** (View on GitHub) link instead. The image dialog supports fit (enlarging or shrinking the complete image to the available area, including after resizing), original size, zoom buttons, Ctrl+wheel zoom, dragging and touch pinch/pan. With several images in the same issue, Previous/Next buttons, left/right arrow keys and horizontal touch swipes browse the description and loaded comments in their displayed order. Each image opens fitted to the viewport; zoomed images keep drag/pinch panning, and Escape returns to the original thumbnail or link. Clicking an image link opens the same viewer, even when its thumbnail has not loaded; modified clicks retain normal link behavior.
- **Recover from network trouble:** API reads have a 30-second deadline through the complete response body. New requests respect GitHub’s recorded Retry-After even within a repository’s queued timeline reads. A manual refresh queued behind a partial update still retries projects that just entered local failure backoff; GitHub’s server wait remains authoritative.
- **Ready when you return:** encrypted local sign-in and content cache, with automatic GitHub updates. Full refresh still revalidates issue and label lists, while reusing a known work start only when the same signed-in client, repository, issue metadata and work-label interpretation still match. Changed or unknown starts and earlier timeline errors fetch history again; restored sessions establish fresh evidence. Repositories with active work are checked every 15 seconds with one conditional request each, so unchanged checks do not use your GitHub rate limit and do not rewrite the encrypted cache; hovering (300 ms), focusing or clicking a repository in the sidebar refreshes just that repository when its last successful refresh is over 5 minutes old, at most once per minute, never in parallel with another refresh and silently skipped while rate-limited or near the quota; sub-issue relations reload when an issue changes, on a full refresh or after 10 minutes. Account settings are encrypted per account on this device and come back when you sign in again after logout. Signing out returns navigation to Overview, so Statistics opens directly on the first click after signing back in.
- **Optical sync:** transfer account, chosen settings and view in either direction using a local QR code. Scan from the QR popup or Settings while signed in; browser permissions and read markers stay on each device. Codes carry a compact binary profile as QR numeric digits, keeping them small enough for laptop webcams; older base64 codes remain readable. A link or scanned code for a different account never replaces a saved sign-in without a confirmation naming both accounts; canceling keeps the saved session.
- **At your desk or on your phone:** responsive columns, keyboard controls, Swedish and English.
- **Light or dark:** Settings → Theme offers Auto (default), Light and Dark. Auto follows your device’s color scheme live; a manual choice overrides it. The choice is saved per browser, survives reload and logout/login, and applies before the first paint so dark mode never flashes light. Colors are CSS tokens redefined for dark mode, with readable text, charts and repository colors. Secondary text meets AA contrast in both themes, and compact metadata stays at least 10px, including on narrow phones.
- **Plan from the overview:** Open issues and In progress summary badges show summed estimated story points and the same calibrated remaining-time horizon as the board columns. Counts and points share the current global and repository filters. Repositories run in parallel; the slowest determines the forecast. Remaining time subtracts time already spent: each issue's own in-progress time and its sub-issues' time (running, or closed within the 30-day window) are deducted from the parent's estimate, whether the parent is in progress or in the backlog, and sub-issues of an estimated parent are not counted again. A parent's own card and list row use the same group rule once its sub-issues have loaded, and the overview story points count a parent and its sub-issues once, with the parent's points, in the column where the group's time is counted. Column counts and points use the same groups, and a column tooltip notes when the heading's card count differs; across repositories each sub-issue is counted only in its own repository. Time for a partly calibrated selection is labelled with its repository coverage, and missing history leaves the time hidden. Estimate clocks stay inside the badges and pause in Statistics. The Repositories card shows how many selected repositories are private and public (plus the owner count when there are several owners), and the Closed card shows the summed story points of the counted closed issues and the median time worked on those with a known start, which is hidden when no start is known.
- **Statistics loading coverage:** The shared progress panel shows an activity spinner throughout source checks and commit loading, with a percentage bar once the commit workload is known; its subtle green styling separates progress from supporting details. A thin track below each chart shows the confirmed loaded span for its selected metrics while collection runs. Sorted update pages and completed commit diffs extend it; unordered issue events require their full list, and sparse old activity alone never proves coverage. The track follows the chosen period, uses existing batched previews and disappears after collection.
- **Explore activity:** Overview and Statistics reuse the same repository card frame and identity heading, with an avatar, owner, description, private badge and accessible collapse control; each view supplies its own controls and content. Statistics stacks the repositories selected in the sidebar in board order, with aligned, equally sized repository filter fields and shortened section names when all selected repositories share one owner (full names remain in tooltips), with issue, commit, code-change and pull-request charts from the latest 30 local calendar days. “Split by repository” starts checked. Uncheck it for one combined graph and totals using every selected repository and its own label/contributor filters; this also loads repositories collapsed in split mode. Counts and code changes sum, closure age and estimate deviation pool their underlying observations, and time per SP is omitted across multiple repositories because each calibration has its own basis. Shared time controls and project filters survive switching modes; returning to split restores its collapse choices. The layout toggle is view-local. Only the first repository is expanded initially in split mode. In split mode, collapse choices persist with the account’s encrypted settings across reloads; collapsed repositories send no statistics requests, including background collection. Expanding a repository loads it on demand, Refresh updates only expanded repositories, and collapsing during collection stops further requests after any already in flight. Filters and chart choices remain intact; clicking a sidebar link expands, loads and scrolls to that repository without leaving Statistics. In both Overview and Statistics, activating the same focused sidebar repository again toggles its collapsed state; in the combined board it toggles the repository’s settings section. One compact time row applies to every repository, with the period on the left and interval/resolution dropdowns on the right: presets (8 hours to 30 days) keep the From/To pickers hidden; choosing Custom reveals local date-and-time pickers filled with the selected window, a period label shows the displayed dates and duration, and the resolution can range from minutes to days (30-day windows require at least six-hour resolution). The shared time zone appears beside your account in the top bar, rather than after normal Statistics timestamps (ambiguous autumn times retain an offset). Displayed times follow your browser’s time zone and daylight-saving changes; saved windows and QR sync preserve the same absolute instants across devices. Each repository groups its totals into Issues, Pull requests and Code for that same period; the totals are buttons that choose which lines the chart shows, in matching colours. Metric groups use compact full-width rows whose tiles fill the available space. In combined statistics, repository sections without available filters are hidden below the shared graph. Label and contributor filters sit in each remaining repository heading with removable chips; charts are followed directly by the source timestamp, without contributor or label breakdown lists. Available badges and charts fill in gradually while statistics are loading, and refreshes retain prior data until new results arrive. Intermediate updates are batched across repositories; only finished collection results are saved to the encrypted cache. Loading feedback stays brief and repeats no period details: a spinner with the source checks, then, once the commit-detail workload is known, completed commits and a percentage; approximate time remaining appears only after at least three fresh detail results and two seconds of measured throughput. This progress is never persisted. Time controls refresh local calendar boundaries after midnight and queue one fresh collection behind any request already running. An Estimates group per repository shows Time per SP, the board's calibrated time per story point over the selected period, and Deviation from estimate, the median of actual ÷ estimated time − 1 for issues closed in each interval; both can be charted, follow the label and contributor filters and are hidden when there is no basis. When metrics with different units are charted together, the second unit gets its own labeled right axis; at most two units are shown at once, and choosing a third replaces the oldest with a short notice. Unavailable metrics stay hidden; bounded API collection is marked when incomplete, including a coverage note for the selected chart metrics. Event pagination follows up to 100 pages, and code metrics include every collected non-merge commit (up to 300 freshly listed or 600 with reused history). Busy repositories therefore retain older activity beyond the former 500-event and 60-diff cutoffs. The first load can need more requests; immutable commit details are reused on later refreshes. Chart height adapts to the number of time buckets and viewport height; short periods stay compact while lines, points and labels keep a consistent readable size. Hover a chart to read every series at the selected point in a compact popover; touch and a keyboard slider (shown only while focused) provide the same values without a permanent chart-time row. Encrypted statistics restore immediately on return (up to 10 repositories, 8 MiB, seven days). While you stay on the board, statistics are also collected quietly in the background so Statistics opens without loading: starting 30 seconds after sign-in, one repository at a time in idle moments, for up to 10 expanded repositories within the same 8 MiB cache. Collection pauses in hidden tabs, offline, with Data Saver, reduced-data preference or low battery, near the GitHub rate limit or after Retry-After, while the board syncs, shortly after you type, click or scroll, and while Statistics is open. Complete commit history reuses historical days and overlaps the previous last UTC day; immutable SHA diffs are reused. Issues, events and PRs are revalidated, and full commit membership is checked every seven days or with Refresh. Issues reuse the board's lists when they were confirmed within the last five minutes, and other lists revalidate with ETags, so unchanged data costs no rate limit.
- **Active projects:** the larger overview cards group each heading, main count, estimates and secondary figures. The Repositories card uses the same active group as the sidebar: projects with Backlog or In progress issues, plus projects still loading. Fully loaded projects with only closed issues are inactive, but only once the **Inactive after** time has passed since their most recently closed issue (see below). Custom work labels and the coordination filter apply; text search and hiding projects from the board do not change the active count.
- **Pending closures:** when a sync no longer contains an issue that was in progress (or closed minutes ago), typically because GitHub's closed list lags just after closing, the card stays in Closed with a dashed outline and an hourglass “Verifying closure” badge (list rows show a “Verifying” status and an hourglass “Verifying” label in the time slot). One single-issue request verifies it at once, within the rate-limit, Retry-After and low-quota guards: a confirmed closing becomes a normal closed card, a reopened or moved-back issue returns to its actual column, and a deleted, inaccessible or transferred issue is removed. Failed checks retry after 5, 10, 20 and 30 seconds; after two minutes without an answer the card is dropped and that repository is fully refreshed. Pending cards exist only in memory and are never written to the encrypted content cache; the hourglass pulse stops with reduced motion.
- **Status moves:** when a sync changes an issue's status (Backlog, In progress, Closed, including a jump straight to Closed, a reopening or a pending closure), its card or row glides about 0.4 seconds from the old column to its new place in Cards and List, on split and combined boards; several moves run together. Only syncs animate: first load, cache restore, filters, sorting, column limits and Cards/List switches do not. When one end is off-screen (for example stacked phone columns) the card instead gets a short outline pulse where it landed, without scrolling. The real card moves (no copies), so focus inside it is kept. Reduced motion shows the final state at once; the movement marker and pending closures work as before.
- **New work:** issues created in Backlog after startup get a green “Created in backlog” marker until read or expired. Returning work keeps its separate movement marker.
- **Project artwork:** Project artwork discovery also checks conventional `img` and `images` directories (including under `public` or `assets`) through GitHub Contents, for member and external public projects. Discovery keeps its six-request budget; older cached misses are retried once after the expanded search is installed, while positive artwork stays cached.
- **Event history:** The header bell opens a compact list with severity, repository and timestamp grouped above each readable message. Issue state changes, including integration handoff, are information events in the account’s encrypted event history. Informational events observed while the dashboard is visible and focused are retained as seen; only information arriving while hidden or unfocused increments the notification badge. Warnings and errors always contribute until read. The badge uses the highest unseen severity: green for information, orange for warnings, red for errors. Initial loads and unchanged refreshes do not create state-change events. Connections dropped or content-cache writes interrupted while the page is hidden, frozen (for example a suspended phone) or offline create no error or warning; the board keeps its content and syncs again when the page returns or reconnects. Genuine access, rate-limit and foreground network failures are still reported. When several projects recover in the same sync, one information event names them all instead of one event per project.
- **See changes:** Overview counts and their sub-values briefly highlight increases and decreases (sub-values float a short +1/−1), with a daily count of loaded issues closed today in your local timezone.
- **Issue sizes:** cards and list rows show story points, including combined boards and phones. An unambiguous positive safe-integer label such as `sp-1`, `sp-2`, `sp-4` or `SP: 5` overrides local sizing and appears as “4 SP”, with its label source in the tooltip. Equivalent point labels agree; conflicting values fall back to local 1/2/3 sizing, shown as “≈ 3 SP”. Overview totals omit “≈” only when every contributing size comes from a label and the sum is safely representable; mixed totals remain approximate. Points also drive column and individual time forecasts, independently of available timing history; time forecasts remain approximate. Expanding a desktop list row keeps the badge on its summary; phone popups show it on the full card.
- **Column estimates:** the In progress and Backlog headers show a compact forecast such as "≈ 25 min left" and "≈ 3 h 10 min". Calibration uses the most recent 30 eligible issues closed within a rolling 30-day window, with at least three known positive In progress-to-closed durations. Each issue uses an unambiguous positive safe-integer points label when present, otherwise rough points on a 1/2/3 scale: cleaned title/body vocabulary, distinct scope items and bounded risk signals provide a local heuristic. Local sizing is capped at 3 after a historical replay found that larger text-derived scores exaggerated duration differences (see [the audit](estimate-calibration.md)); explicit labels keep their full values. Cached Statistics sizes migrate to the same cap without losing activity history. Repeated boilerplate, pasted code and logs do not automatically imply more work; these points are not measured complexity. Before calibration, durations per story point above four times the raw window’s median are excluded as suspected interrupted runs; ordinary overruns and proportionately larger issues remain. At least three samples must remain. The retained samples determine time per point, typical duration and historical parallelism, including closed-issue comparisons (which exclude the issue itself before filtering). Actual closed-issue durations remain visible. The repository median duration per point sets each issue’s expected time. In progress subtracts elapsed time and shows the longest remaining forecast; Backlog adds its point total × time per point ÷ measured parallelism. Combined boards show the slowest repository. Tooltips explain the points, calibration window and rate. The header’s own clock updates elapsed time and ages out expired history; nothing is shown without enough usable evidence. Board clocks never run behind timestamps received from GitHub: when the device clock is slow, elapsed times, ages and forecasts count from GitHub’s latest known time instead of standing at 0m 0s or showing new issues as created in the future.
- **Spot stalled work:** Settings can disable estimate-based warnings or set an allowed overrun from 0–1000% (default: enabled, 25%). In-progress work is flagged only after its calibrated total estimate plus that tolerance, with a reliable start and sufficient history. Warning text on cards and list rows uses the estimate; foreground and background notifications follow the same rule. Settings and calibration changes establish a silent notification baseline, preserving one notice per work period. Older fixed-minute preferences migrate to the new defaults; the new choices are encrypted per account and follow QR sync. Time labels update on their own: seconds only while shown on screen, and not at all in hidden tabs or while Statistics is open, so large boards stay light. Separately, an open In progress issue with a known work start shows “Possibly stalled” after one hour without a visible issue update. Cards show the idle duration; list rows show an accessible warning icon and reveal the text when expanded. Any fresh issue activity clears it after sync. This is independent of estimate warnings and only suggests investigation: agents can work or update a coordination thread without changing the issue, and fresh metadata is not proof of progress. Closed issues, Backlog, coordination threads and unknown work starts have no inactivity warning.
- **Waiting for integration:** an open issue labelled `integration-ready` (also `integration_ready` or `Integration Ready`) stays in In progress, so handed-off work does not fall back to Backlog, but it is not active work. Cards show a purple “Awaiting integration” badge with a merge icon instead of the running timer; list rows show a compact “Waiting” badge with the same icon (icon only on the narrowest phones) and the full status for screen readers. Its tooltip gives the active working time reached so far. While waiting, the active time stops, no timeout or “Possibly stalled” warning appears, it does not count as running work for remaining time or parallelism, and it does not mark the repository as having observed work activity. Counts, filters, column estimates and the overview still treat it as In progress. When active work resumes (`in-progress` again, for integration or a correction), the timer continues without the wait and keeps the original In progress start, so the card does not jump; a handoff made as two separate label edits up to five minutes apart still counts as one period. Measured work time of closed issues and Statistics closings exclude these waits. With both labels, active work wins; closed issues stay Closed. A repository's custom work label replaces only the active-work labels: `integration-ready` stays recognized. Owner labels remain ownership only.
- **Hear progress:** open a repository’s properties to enable its notifications for distinct sounds when work starts, closes, becomes blocked or returns to Backlog. Mute notification sounds separately in Settings while keeping repository and browser notifications; the choice is saved per account. Clicking a status notification brings the dashboard to the front, opens Overview and highlights the issue with a pulsing frame (static with reduced motion); a collapsed repository, a Show more limit or a search that hides the issue is opened up, and an issue the board cannot show leads to its repository. Audio resumes after interacting with the dashboard; browsers may delay background updates.
- **Notifications while closed:** the installed app in Chrome or Edge can notify you about closed, started, returned, reopened and timed-out issues in repositories that are selected with notifications on, even when no window is open. See [limitations](#background-notifications).

- **Project details:** sidebar projects keep the full-height artwork beside a dedicated name line and counters/unread activity below it. Names use the complete text width and retain canonical full-name tooltips. Hover or focus reveals an ellipsis on the artwork; on touch the cue remains visible. Click/tap the artwork action or tab from the project link to open its context menu with GitHub, available Pages and show/hide actions. Arrow keys, Home and End move between actions; Escape returns focus to the artwork action, and clicking outside closes the menu. Menus use the browser's top layer and stay inside the viewport even when the sidebar scrolls. Workspace navigation shares the project section's width and small inset. The compact license link opens LICENSE in a new tab and keeps author details in its tooltip.

Issueflow reads GitHub. Make issue changes on GitHub; private content stays in your browser's encrypted storage.

## Background notifications

Background checks use Periodic Background Sync and work only in Chromium browsers (Chrome, Edge) with Issueflow installed as an app, signed in and with notification permission granted. Safari and iOS are not supported; other browsers notify only while the dashboard is open.

- **The browser decides when to check.** Issueflow asks for about one check per hour, but the browser chooses the interval from its own engagement and battery heuristics, often several hours apart and never guaranteed. Checks may stop entirely while the device sleeps or the app is rarely used.
- **The first check is silent.** It records a baseline; later checks notify only about changes since the previous check. Checks older than 24 hours start a new silent baseline, so stale changes are not announced. An open, visible app window announces changes itself and the background check only updates its baseline.
- **Everything stays on the device.** There is no server, webhook or push service: the browser wakes the service worker, which reads the token and settings from the encrypted local stores, asks GitHub directly and keeps the last seen state as AES-GCM ciphertext in IndexedDB. Logout clears it with the rest of the content cache.

## Connect

Use a fine-grained GitHub token with **Issues: read** and **Metadata: read**. Add **Contents: read** and **Pull requests: read** for private closing commit details. Try the demo first—no account required. Stored credentials and active sessions are hardened by a Content-Security-Policy (CSP) meta tag in `index.html`; new external origins (such as an OAuth auth worker) must be added to the CSP in `index.html`.

Settings includes **Show GitHub username in projects** with **Auto | Yes | No**. Auto is the default for existing accounts: combined board chips omit an owner shared by all selected repositories; sidebar names use the same shared-owner rule across sidebar projects, independently of board layout. Yes always shows `owner/repository` in existing repository chips and sidebar names; No always shows the repository name, including colliding names across owners. Full repository identities remain in tooltips and accessible labels. The choice is encrypted per account, survives sign-out and reload, and transfers with optical preferences; older transfers preserve the receiving device’s choice.

**Hide coordination issues** is in Settings → Board. It starts enabled and keeps the same encrypted account preference and filtering across board groupings.

Settings groups appearance, board, notifications and time estimates with consistent form fields and checkbox toggles. Desktop settings use two columns; phones keep one column with touch targets. Permissions, workflow instructions, automatic updates and QR scanning remain available below. Update prompts stack their action buttons vertically and show the ten-second countdown inside Update now (10); opening a dialog pauses the countdown, while Not now defers until tomorrow. The sidebar version tooltip and accessible status show whether a check confirmed the latest version, found an update, or has not completed. The Issue workflow instructions button opens a compact popup with the full bundled Markdown in a scrollable textarea and a Copy instructions button.

**New repositories without signing in again:** while the app is open and visible, a signed-in session rechecks the repositories the token can access about once an hour, and again when the selection dialog opens on a list older than five minutes. A hidden, sleeping or offline app sends nothing; returning catches up with one check, not one per missed hour. The request is ETag-conditional, single-flight per account, waits for rate limits and Retry-After, and a response that arrives after an account switch or sign-out is discarded. New repositories appear in the selection dialog unselected; selections, order, colours, filters, collapsed sections and other people's public projects are unchanged, and a selected repository missing from the list stays selected so the board reports its real status. Failures keep the last list silently and retry after at least ten minutes (#421).

The selection dialog shows each repository's project icon (or initials with the workspace colour) beside its name. Icons are requested only for rows scrolled into view, three at a time, through the existing 24-hour resolver cache and encrypted content cache, and appear one by one without delaying the list (#421).

Settings → GitHub permissions shows verified access and explains which features each read permission enables. A red Settings badge counts permissions with confirmed missing access that you have not viewed. Viewed notices stay acknowledged per account on this device after reload or logout/login; the permission table keeps showing the actual access results.

The sidebar shows the running short commit above the license link; its tooltip keeps the full build date, commit and update status, and clicking it opens Release notes. Settings → Automatic updates shows the full build identity. When a new version is published, every open tab, visible or in the background, shows a short summary of what changed and installs it after a 10-second countdown shown in **Update now (10)**. Open dialogs pause the countdown and closing them restarts the full ten seconds. **Not now** postpones the automatic prompt until the next calendar day in your time zone (remembered on this device, also for background checks). Until the update is installed, a red (!) badge on the sidebar version (beside Menu on phones) opens the update view, also available from Settings → Automatic updates. Automatic checks run every minute and when returning to the tab, including after a previous hard reload left the page without a service-worker controller. Updates keep encrypted sign-in, settings and cached content; offline or failed activation keeps the current version running.

## Release notes

What's new is written per day in Swedish and English in [`src/release-notes.json`](../src/release-notes.json), newest day first. Each day has a short summary and a few readable sections about user benefit, each listing the related issue numbers. Only changes published on `main` are included; no secrets or private repository content.

The build bundles the notes and also publishes `release-notes.json` next to `index.html` with the build identity (`builtAt`, `commit`). An older installed version can fetch it without a token, sign-in or AI access to show what changed since it was built; the file is always fetched from the network, never from the app-shell cache.

Keeping notes current: every published user-facing change adds to or updates that day's entry (Europe/Stockholm date) in the same commit. Merge related work into the existing sections rather than adding one line per issue or commit, and do not describe unpublished or later-replaced behavior. `tests/release-notes.test.ts` validates the file.

## Run locally

Requires Node 22.20+.

```sh
npm ci
npm run dev
```

Use Node.js 22. `npm ci` applies the version-23 jsQR compatibility correction used by optical profile sync.

Run affected tests locally before pushing; use `npm run build` for code changes. Stories move **Backlog → In progress → Closed**: close them after integration on main and successful local verification/review. Publication is separate; finished stories stay Closed while a technical `needs-deploy` marker and the prepared release delta track publication follow-up. Remove that marker after verified publication; reopen only for unmet acceptance. Integration pushes are allowed while work remains; GitHub Actions decides publication through a fresh issue/delta gate before building and again before deployment. Unfinished or active issues block publication; locally verified, unclaimed `needs-deploy` issues must appear in the prepared delta. Finished handoffs waiting as `integration-ready` block only inside the prepared delta: outside it their code is not on `main`, like unclaimed backlog. If nothing has been published for 3 hours, an hourly scheduled run publishes the finished batch even while other issues are still active, so `main` only ever receives finished work. Manual deployment never bypasses the gate. Orkester watches for new issues every minute for 60 minutes after the last verified release; new completed work restarts that window. Generate the popup summary in `src/update-summary.json` from that publication’s delta against the previously deployed build (maximum 180 characters per language). Full daily notes remain available through Read more. The build rejects unresolved merge markers, including those that would otherwise render as text in Vue templates. Browser tests need a one-time `npx playwright install chromium`. Actions only builds and publishes.

### Observed repository work activity

Repository headers and the Repositories overview show an optional work-activity indicator
when an open, non-coordination issue carries the repository's configured work label
(default: the existing In progress detection) and its GitHub `updated_at` is less than
60 minutes old. An issue that only waits for integration (`integration-ready`) is not active work and does not qualify. Future or invalid timestamps, failed/loading repositories, PRs and closed
issues do not qualify. The indicator expires on the next minute tick and recomputes on
ordinary refresh; removing the work label or closing the issue removes its evidence.
It uses all selected repository data, including coordination issues hidden by board filters.

Open the indicator by keyboard or touch to see recent issue counts, the latest observed
change and a link to the most recently updated open coordination issue, if present.
An owner claim (`orkester: <session>`) on qualifying work plus that coordination issue
changes the header caption to Orchestra activity. Neither a coordination update nor an
owner claim qualifies alone. GitHub metadata/comments are only an estimate of activity,
not proof of a live process. There is no machine-readable heartbeat identifying individual
agents in the available issue data, so no agent count is inferred or deduplicated from
issues, claims, commenters or sessions. The overview counts repositories with evidence.

Projektikoner som tidigare inte hittades kan hämtas igen med projektets uppdateringsknapp eller F5/Ctrl+R. Befintliga ikoner återanvänds; bakgrundsuppdatering och hover gör inga extra ikonförsök. Äldre tomma ikonposter från första ikonversionen granskas en gång efter uppdateringen, därefter gäller fortsatt dygnscache, krypterad lagring och kvotgränser (#395).
