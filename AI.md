# AI workflow

This file applies to all work in this repository, regardless of which AI tool performs it. Read it before making changes. The user's current instructions take precedence.

## Issues and priority

- Every change needs a GitHub issue before implementation, including documentation, fixes, features and workflow changes. Reuse an existing issue when its scope already covers the work. Include concrete acceptance criteria.
- Every issue must carry exactly one of `priority: high`, `priority: medium`, or `priority: low`. When creating an issue, automatically assess its priority from user impact, severity, urgency, affected scope and available workarounds instead of routinely assigning medium. The user's explicit priority always takes precedence; do not change an existing priority without user direction. This rule applies to every agent, including the conductor and workers under `/orkester`.
- Use `priority: high` for blocking bugs, significant regressions, broken core flows, data loss, security problems or other time-critical failures. Bugs and regressions should normally outrank comparable feature requests; a `bug` label alone does not make a minor cosmetic defect high priority.
- Use `priority: medium` for useful features, workflow improvements and limited bugs with a reasonable workaround. If the impact is unclear, make a provisional medium assessment and briefly state what is uncertain rather than inventing severity or blocking issue creation on routine clarification.
- Use `priority: low` for minor cosmetic defects, optional polish and small documentation improvements without meaningful functional impact. Assess actual impact even for documentation: incorrect instructions that cause data loss or block setup may warrant higher priority.
- Include a short priority rationale in each new issue's body, describing the impact or urgency behind the chosen label. Before creating the issue, check that the rationale and the single priority label agree.
- Follow [the canonical Issue workflow instructions](public/ISSUEFLOW.md) and the
  shared [authority procedure](.orchestra/shared/ISSUE-WORKFLOW.md) for labels/status.
  Add `in-progress` immediately before actual work; remove all recognized work labels
  when paused, awaiting integration, handed back, finished, closed or reopened. Owner
  labels are separate from work status and priority. Share one resolved guide per session.
- Orchestration capacity, active-claim accounting, file ownership and handoff rules are
  defined once in [.orchestra/project.md](.orchestra/project.md#capacity-ownership-and-progress).
  Preserve its measured capacity (including conductor work), fresh queue checks before
  assignment/resume/integration, and release of inactive claims during integration waits.
- When scope expands, create or update the relevant issues. Keep unfinished work tracked and explain any actual blocker on its issue.
- Questions for the user never pause unattended work. Make routine decisions yourself from sensible defaults and record the reasoning on the issue. When a decision genuinely needs the user, post one issue comment with concrete options and a recommendation, add the `user question` label, release your claim and continue with other work. Skip `user question` issues when selecting work until the user has answered; whoever resumes removes the label. `user question` does not block publication; reserve `blocked` for real technical blockers, because it stops the Action gate.

## Implementation and Git

- Inspect `git status` and preserve work you do not own. Use `rg` to find relevant code and project instructions.
- The user has authorized committing and pushing directly to `main`; no PR or additional confirmation is required for this project's requested work.
- Resolve merge conflicts completely, including markers inside Vue templates that can compile as visible text. Preserve the intended behavior from both sides and verify their integration together. `npm run build` rejects conflict-marker lines in tracked text files; a successful type check alone does not establish a clean merge.
- Keep commits scoped to an issue. Reference it with `Fixes #N` when acceptance criteria are satisfied. Remove `in-progress` when closing it. Do not close an issue merely because implementation has started.
- Integration pushes to `main` are allowed while work remains. GitHub Actions alone decides whether to publish: its complete paginated issue gate runs before building and again immediately before Pages deployment. Any active, blocked or owner-claimed issue prevents publication, as does any issue included in the prepared delta without `needs-deploy`. Unclaimed backlog issues without `needs-deploy` outside the delta do not block. Fallback: when the public build is at least 3 hours old and `main` has unpublished changes, active, blocked or claimed issues outside the prepared delta no longer block, so finished work reaches production while much remains; every other check still applies, and the workflow also runs hourly on a schedule for this. Therefore `main` must always be publishable: never integrate unfinished work on `main`, even with an active claim; keep in-progress and paused work in its worktree/branch, and keep `src/update-summary.json` and release notes current with every integration. Ignore pull requests and issues carrying the exact coordination label `orkester`; `orkester: <session>` is an owner claim, not a coordination exemption. Never replace or bypass this gate with a manual deployment.
- Mark implemented, integrated and locally verified work `needs-deploy`, without `in-progress`, `blocked` or owner claims. Open ready issues may pass the Action gate only when included in the prepared publication delta; closing issues is not required to unblock deployment. Preserve commits/worktrees and issue references. Pushes, issue opening/reopening/closing/label changes and gated workflow dispatch recheck readiness. The Action never edits readiness labels. After successful publication, verify Pages, close delivered issues and remove `needs-deploy`; never mark unfinished work ready just to publish.
- Prepare the short AI update summary in `src/update-summary.json` from the locally verified batch’s actual user-facing delta against the public `release-notes.json` build. Record that exact published commit as `baseCommit`, keep each Swedish/English summary at most 180 characters, and list only included issues with traceable daily release notes. Both Action gates verify the current main SHA, published baseline and prepared delta; the final gate also checks the exact built artifact. Missing, stale or unreadable metadata blocks publication, and an already published SHA is skipped. The automatic update popup describes this latest publication only, never all changes from a calendar day or a concatenation of daily summaries. Keep daily release notes compact and link issues for details.
- Before pushing, fetch `origin main`, inspect divergence, and rebase your own commits if necessary without overwriting someone else's changes. Preserve unpublished subtree merge ancestry with `git rebase --rebase-merges origin/main`. Never force-push `main`.
- Verify appropriate behavior locally, then verify the GitHub Actions / Pages deployment after pushing. Resolve failures before reporting completion.
- Run tests locally before pushing, selecting only behavior that the change can reasonably affect. Do not routinely run or repeat the full suite. GitHub Actions only builds and publishes Pages; do not add test runs or browser installation to the deployment workflow.

## Project and verification

- Vue 3 + TypeScript; static frontend hosted at `https://solwation.github.io/github-dashboard/`.
- GitHub issue state and labels are authoritative. The dashboard reads GitHub; changing an issue requires an explicitly requested write feature.
- Follow the existing detection rules and per-repository overrides rather than hard-coding private issue contents or account credentials.
- Show optional features only when their relevant data is available to the current PAT. When data or access is missing, hide the affected section, control or metric without empty placeholders, unavailable notices, or token/permission warnings. A meaningful measured zero is valid data; do not hide it as missing. A loading indicator may appear while an actual request is pending. Keep permission explanations in the explicitly opened GitHub permissions view and preserve genuine authentication and core data-refresh errors. Apply this rule to future features as well as existing optional details such as closing commits and Statistics.
- The user requires encrypted persistent sign-in: store tokens only as AES-GCM ciphertext in IndexedDB with a non-exportable key, never plaintext in localStorage or published assets. Delete the credential only after explicit confirmed logout; preserve it on reload and transient API errors. The user also authorizes an encrypted, bounded IndexedDB content/ETag cache for immediate startup followed by GitHub revalidation. Bind cached content to the saved credential, never mix accounts, restore the saved identity and board optimistically without routine startup notices, report genuine restore or refresh errors while preserving the board, and clear the cache with confirmed logout or changed credentials. Account-bound settings (selected repositories, order, label rules, filters, notification subscriptions, Statistics filters, read markers, permission acknowledgements) are stored per login as AES-GCM ciphertext in a separate IndexedDB database with its own non-exportable key, bound to the login; they deliberately survive confirmed logout and are restored when the same account signs in again, never for another account. Never keep repository names, issue ids or contributor names in plaintext localStorage/sessionStorage; only non-private preferences such as language, theme and update deferral may stay there. Credential-bearing QR transfers are generated locally on demand and must never be committed or cached. Do not commit tokens, client secrets, or private issue snapshots. Keep private content out of service-worker/HTTP caches and plaintext storage.
- Keep keyboard access, accessible names, mobile layouts and `prefers-reduced-motion` support when changing UI behavior.
- For every UI change affecting issue cards or list rows, use Playwright to verify both Cards and List in four scenarios: wide desktop (for example 1600×1000), narrow desktop (1000×900), portrait phone (390×844), and landscape phone (844×390). Phone scenarios must use a mobile/touch browser context, not only a resized desktop viewport. Include a narrow phone such as 320×568 when density or truncation changes. Inspect screenshots visually as well as checking geometry: no overlaps, page overflow, misplaced metadata or unexpectedly tall rows. Exercise long titles/labels and relevant timeout, unread movement/comment, estimated/remaining/actual-time states; test split and combined boards when shared layout or repository labels are affected. Reuse one captured public-data snapshot across scenarios where helpful to protect API quota, and never commit real issue responses as fixtures. Keep checks targeted to the change.
- `npm test` checks pure logic and transport behavior. `npm run test:e2e` checks browser flows; run `npx playwright install chromium` once if needed. `npm run build` checks types and production output. Run the checks appropriate to the issue; avoid redundant tests that only mirror implementation.
- For targeted checks use `npx vitest run <affected test files>` and `npx playwright test <affected test files>`. The npm test scripts run entire suites and are appropriate only when the scope justifies them.
- Keep release notes current: every published user-facing change adds to or updates that day's entry (Europe/Stockholm date, newest day first) in `src/release-notes.json` as part of the same commit, in both Swedish and English. Keep each daily summary short and each point to one short sentence, usually 10–25 words, focused on user benefit. Merge related improvements into existing sections instead of one line per issue or commit; avoid repetition and keep the related issue numbers in `issues` so readers can follow clickable links for details. Describe only what is actually published on `main`: no invented or unpublished features, repetition, secrets or private repository details. An integrating conductor writes the entry for integrated worker results. Run `npx vitest run tests/release-notes.test.ts` after editing the file.
- Update `README.md` when behavior or setup changes. Keep this file current when the project workflow changes.

## /orkester

Use [.orchestra/project.md](.orchestra/project.md), which loads the versioned,
model-independent [shared core](.orchestra/shared/ORCHESTRA.md) and queue coordination.
The existing [skill](.agents/skills/orkester/SKILL.md) and
[slash command](.claude/commands/orkester.md) are thin adapters; other file-reading
agents use the same files directly. `/orkester`, `$orkester` or an explicit request
starts the workflow; reading or maintaining these files does not start a queue session.

The user authorizes parallel subagents when useful. The local policy retains measured
capacity including conductor work, one issue per worker, isolated ownership, fresh queue
checks, question routing, Actions-only publication, final review and the 60-minute watch
with minute polling. Shared planning and verification avoid needless splitting or repeated
tests while preserving these project requirements. Instruction-only maintenance checks
its Action outcome without inventing app release notes or bypassing the publication gate.
